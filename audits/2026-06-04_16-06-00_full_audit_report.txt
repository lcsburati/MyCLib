5. MEDIUM SEVERITY FINDINGS (SHOULD FIX)
================================================================================

--------------------------------------------------------------------------------
Finding 1: Signed/unsigned mismatch in Levenshtein loops
--------------------------------------------------------------------------------
Severity:    Medium
Location:    src/string_utils.c -- my_strcmp_percent()
             -- lines 166, 186, 189, 194, 195, 210, 219
Problem:     Loop counters are `int` while the bounds str1_length/str2_length
             are `size_t`. Strict builds emit 7 -Wsign-compare warnings.
Impact:      The signed counter is converted to unsigned for the comparison. It
             is safe here because counters only ascend from 0/1 and lengths are
             bounded by STR_BUFFER (256), but the pattern is a classic defect
             source and produces warning noise.
Recommendation: Declare the loop counters as `size_t`. Note the cleanup loop
             counter `k` (line 173) must also become `size_t` once `i` does, or
             it introduces a new sign-compare warning.
Effort:      S
Confidence:  High

--------------------------------------------------------------------------------
Finding 2: size_t -> int narrowing of max_len
--------------------------------------------------------------------------------
Severity:    Medium
Location:    src/string_utils.c -- my_strcmp_percent() -- line 206
Problem:     `int max_len = (str1_length > str2_length) ? str1_length :
             str2_length;` narrows size_t to int (2x -Wshorten-64-to-32).
Impact:      Lossy in theory; safe in practice because the inputs are bounded by
             STR_BUFFER. Still flagged under -Wconversion.
Recommendation: Store max_len as `size_t`. The `(double)distance / max_len`
             division still behaves correctly.
Effort:      S
Confidence:  High

--------------------------------------------------------------------------------
Finding 3: my_strcmp_percent() error sentinels are unnamed and unchecked
--------------------------------------------------------------------------------
Severity:    Medium
Location:    src/string_utils.c -- lines 144, 154, 163, 180, 214
             (caller: src/main.c, my_strcmp_percent call site)
Problem:     The function returns bare negative magic numbers (-1..-4). They are
             out of the valid range (good) but undocumented in code, and the
             caller does not test for `< 0` before displaying the value.
Impact:      A future caller can misread the value; an error would currently be
             rendered as a negative percentage. (Not reachable from the GUI,
             where inputs are never NULL and never exceed the buffer.)
Recommendation: Define named constants (e.g. an enum: STRCMP_ERR_ALLOC = -1,
             STRCMP_ERR_OVERFLOW = -2, STRCMP_ERR_NULL = -3,
             STRCMP_ERR_EMPTY = -4) and have the caller branch on `result < 0`.
Effort:      S
Confidence:  High

--------------------------------------------------------------------------------
Finding 4: Public API is not const-correct
--------------------------------------------------------------------------------
Severity:    Medium
Location:    include/string_utils.h -- lines 13-21
             Evidence: src/ui.c:219-220 (AI-generated) emits
             -Wincompatible-pointer-types-discards-qualifiers in the default build
Problem:     `typedef char * string;` plus non-const parameters mean read-only
             functions (my_strlen, my_strcmp, my_strcmp_percent) advertise
             mutable pointers, so passing a `const char *` discards qualifiers.
Impact:      Real warnings at call sites; weaker API contract; const data cannot
             be passed cleanly.
Recommendation: Use `const char *` (or a `const string`) for read-only inputs.
             Keep my_toupper()/my_tolower() returns as mutable heap buffers.
Effort:      S-M (touches the header, the .c signatures, and call sites)
Confidence:  High

--------------------------------------------------------------------------------
Finding 5: my_strlen() still overloads 0 for NULL and empty string
--------------------------------------------------------------------------------
Severity:    Medium (downgraded from High; overflow is now distinct)
Location:    src/string_utils.c -- my_strlen() -- lines 12-30
Problem:     Both NULL (line 14) and a valid empty string (fall-through to line
             30) return 0. Only the overflow case is now distinguishable.
Impact:      Callers cannot tell "empty" from "invalid pointer" by return value
             alone. Lower impact than before since most call sites NULL-check
             separately, but the contract is still ambiguous.
Recommendation: Document the contract explicitly, or adopt a clearly separated
             error signal if my_strlen() is meant to be a bounded helper rather
             than a strlen() clone.
Effort:      S-M
Confidence:  High

7. ARCHITECTURE & DESIGN NOTES
================================================================================

  - Clean layering: the backend (string_utils, math_utils) has no dependency on
    the UI; only main.c/ui.c depend on raylib. This separation is good and makes
    the core unit-testable in isolation.
  - Dependency direction is sane: string_utils -> math_utils (min() for the
    Levenshtein step); no cycles.
  - Memory ownership of my_toupper()/my_tolower() (caller frees) is consistent.
  - The `typedef char * string` alias is a deliberate pedagogical choice but is
    the root of the const-correctness gap (finding 4).
  - Header hygiene improved (stddef.h). Headers still lack include guards issues?
    No -- both headers have proper guards.

9. PERFORMANCE NOTES
================================================================================

  - my_strcmp_percent() is O(n*m) in time and space (full Levenshtein matrix),
    bounded by STR_BUFFER (<= 257x257 ints, ~256 KB worst case). Acceptable for
    this use case. A two-row rolling buffer would cut memory to O(min(n,m)) if
    ever needed, but it is not necessary here.
  - The GUI recomputes results per frame for the active screen; for
    my_strcmp_percent this means a full matrix alloc/free at up to 60 FPS while
    that screen is active. Not a correctness issue and not measured here; only
    worth caching if profiling ever shows it.
